# Dynamic Validation

[vuln-discovery](../vuln-discovery/SKILL.md)의 후보를 받아 실제 실행에서 결함이
발생하는지, 그 결함이 지정된 근본 원인에서 비롯되는지 확인한다. 결과는 최소 재현기,
원본 실행 증거, 인과 분석, 명시적인 판정과 한계다.

## 범위와 배정

- 먼저 `AGENTS.md`와 인계된 `scope.md`, 후보 기록을 읽는다. 동적 검증이 승인된 범위에서
  실행하며, 발굴 요청만으로 재현 실행 권한을 추정하지 않는다.
- 최소 재현기 작성·수정, 격리 실행, 진단과 최소화까지 수행한다. 권한 상승, 플래그 획득,
  완화 우회 또는 익스플로잇 체인 구현은 이 스킬의 완료 조건이 아니다.
- 커널 검증은 `kernel_astra` 역할 또는 정확한 `gpt-6-astra` 모델에 배정한다. 이미 해당
  모델로 실행 중이면 직접 수행할 수 있다. 요청 모델과 실제 확인된 모델을 구분해 기록하고,
  지원되지 않으면 임의로 대체하지 않는다.
- 병렬 검증 시 후보별 작업자, 출력 경로, VM, 빌드 디렉터리를 배타적으로 배정한다.
  작업자는 다른 작업자의 파일을 되돌리지 않는다. 공유 `FINDINGS.md`는 오케스트레이터가
  갱신한다. 별도 인과 검토가 필요한 후보에만 독립 검토 작업자를 배정한다.
- 연구 산출물은 `agent/<research-name>/validation/<candidate-id>/`에 보존한다.
  기존 발굴 기록을 덮어쓰지 않고 원래 Candidate-ID와 Target-ID를 유지한다.

## 1. 인계와 재현 준비

후보마다 다음을 확인한다.

- 정확한 소스 리비전, 설정, 진입점, 공격자 제어, 필요한 권한과 상태
- 위반된 불변식, 예상되는 첫 번째 잘못된 연산, 관련 소스 위치
- 정적 반증 결과, 미확인 가정, 중복·수정 여부
- 재현 성공을 판정할 관측값과 이를 수집할 방법

`SOURCE_CONFIRMED`도 런타임 사실로 간주하지 않는다. `HYPOTHESIS`는 먼저 빠진 정적
근거를 확인한다. 필요한 소스·설정이 없으면 `NEEDS_CONTEXT`로 보류하고, 명백히 반증된
후보는 새로운 증거 없이 반복 실행하지 않는다.

검증 전 후보별 시간, 시도 횟수, 게스트 CPU·메모리·프로세스 제한과 무진전 중단 기준을
정한다. 사용자 제한이 없으면 작업 복잡도에 맞는 유한한 값을 정해 기록한다. 긴 경쟁이나
참조 카운트 래핑 조건을 호스트 자원 고갈로 해결하지 않는다.

## 2. 격리 환경과 대상 일치

PoC와 재현 워크로드는 작업 소유 VM 또는 행위와 목적지까지 승인받은 공식 서비스에서만
실행한다. 컨테이너는 호스트 커널을 공유하므로 이 목적의 격리로 인정하지 않는다.

- VM 생성 전 중지된 디렉터리까지 충돌을 확인하고 `<task>_<unix-timestamp>` 이름을 쓴다.
  profile, 이름, 경로, 생성 시각, 소유 작업자를 기록한다.
- 검토한 `tools/vm.sh`, `tools/kernel.sh`의 현재 CLI를 확인한다. profile은 `-p`, VM은
  `-p <profile> -v <vm>`을 하위 명령 앞에 지정하고 SSH 원격 명령 앞에 `--`를 둔다.
- 파일 전송은 `tools/vm.sh ... scp`와 `vm:` 게스트 경로를 쓴다. 호스트 공유 디렉터리를
  연결하지 않는다. 기존 이미지가 없으면 준비 필요를 기록한다. 호스트에서 마운트를 수행하는
  `fs.sh create`나 `create-image.sh`를 실행하지 않는다.
- 호스트 커널·sysctl·모듈·서비스를 변경하지 않는다. 다른 소유자의 VM을 종료하거나
  초기화하지 않는다. 크래시 복구도 기록된 작업 소유 VM에 한정한다.

`environment.md`에 소스 커밋과 로컬 변경, 커널 이미지·vmlinux·설정의 해시,
컴파일러와 빌드 명령, 부팅 인수, 게스트 이미지, 아키텍처, CPU·메모리, 실제 부팅 커널을
기록한다. `uname` 문자열만으로 정확한 이미지 일치를 주장하지 않는다.

메모리 오류는 KASAN, 경쟁 의심은 KCSAN처럼 가설에 맞는 진단을 선택한다. 실제 설정과
활성 상태를 확인하고, 대상 설정에서 진단용으로 변경한 항목을 명시한다. 계측·지연 삽입·
fault injection은 별도의 실험 조건으로 기록한다. 결함을 만들도록 로직을 변경한 실험은
원래 후보의 재현 증거가 아니다.

KernelCTF 대상이면 작업 시점의 공식 규칙, 대상 이미지와 시작 권한을 읽기 전용으로 확인해
적격성을 별도로 기록한다. 원격 실행이 승인되어 있으면
[kctf-official-helper](../kctf-official-helper/SKILL.md)를 읽는다. 인증서나 접속 도구의
존재만으로 공식 시도·업로드·제출 권한을 추정하지 않으며, 이미 받은 승인은 반복 요청하지 않는다.

KernelCTF 규칙이 hardened 대상의 악용과 별도로 LTS에서 `--vuln-trigger`에 의한 충돌을
요구하면, LTS 재현은 이 단계의 별도 실험으로 기록한다. 대상마다 정확한 릴리스·설정·해시를
남기고, KASAN 전용 충돌과 비계측 LTS 충돌을 구분한다. 한 대상의 성공을 다른 대상의 성공으로
대체하지 않는다.

## 3. 최소 재현기와 증거 기반 반복

1. 공격자 진입점에서 문제 연산까지 필요한 동작만 포함하는 읽기 쉬운 재현기를 작성한다.
   시스템 호출 반환값과 errno, 진행 단계, 입력·seed를 기록해 도달 실패를 구별한다.
2. 컴파일 명령과 소스·바이너리 해시를 보존한다. 호스트에서 빌드하더라도 실행·스모크 테스트는
   게스트에서만 수행한다.
3. 관리자 준비 작업과 공격자 동작을 나눈다. 실행 시 UID/GID, capabilities, namespace,
   파일·장치 접근 권한을 기록한다. root SSH 접속 상태에서 실행한 결과를 비특권 재현으로
   표시하지 않는다.
4. 실행 전에 게스트 콘솔 수집을 시작하고 시간 제한을 설정한다. stdout/stderr, 종료 코드,
   커널 로그, 콘솔 원본을 시도별 경로에 보존한다. SSH 단절에 대비해 콘솔 증거를 확보한다.
5. 실패하면 마지막으로 도달한 단계와 예상 경로를 비교한다. 입력 거부, 설정 누락, 권한 부족,
   순서·타이밍 문제, 계측 부재, 인프라 실패를 구분한다.
6. 새 관측이 뒷받침하는 변경만 적용한다. 매 시도마다 변경 이유, 입력, 환경 차이와 결과를
   기록하고 성공·실패 로그를 덮어쓰지 않는다.

KASAN 보고가 없다는 사실만으로 안전하다고 결론 내리지 않는다. 진단 범위, 경로 도달,
시도 횟수와 관측 누락을 확인한다. KCSAN 보고는 데이터 경쟁의 증거이며 그 자체로 메모리
손상이나 보안 영향을 입증하지 않는다. 비메모리 결함은 기대 상태와 실제 상태를 비교하는
구체적인 관측 기준을 사용한다.

## 4. 인과관계 확인과 최소화

크래시가 발생하면 먼저 실행을 반복하기보다 원본 증거를 확보한다.

- 해당 빌드의 심볼로 스택을 해석하고 최초 오류 위치, 접근 종류·크기, 객체 수명과
  할당·해제 스택을 후보의 소스 경로에 연결한다.
- 입력 → 상태 전이 → 불변식 위반 → 런타임 관측의 연결을 설명한다. 손상 이후의 2차
  크래시나 sanitizer의 요약 한 줄만으로 근본 원인을 단정하지 않는다.
- 지정된 후보와 다른 버그가 트리거되면 별도 관찰로 기록하고 원래 후보의 성공으로 세지 않는다.
- QEMU, SSH, watchdog, OOM, 잘못된 이미지 등 인프라 실패를 커널 후보와 분리한다.
  호스트나 격리 경계를 조사 대상으로 확대하지 않는다.
- 불필요한 호출·입력·스레드를 제거하고, 최종 재현기로 깨끗한 게스트 상태에서 다시 시도한다.
  실행 순서·동시성·seed·소요 시간과 성공 횟수/총 시도를 함께 남긴다.
- 가능하면 핵심 트리거 조건을 제거한 대조 실행을 수행한다. 대조에서 발생하지 않았다는
  사실만으로 인과관계를 확정하지 말고 소스와 스택 근거를 함께 사용한다.

계측이나 특권을 추가한 조건에서만 확인되었다면 그 조건을 유지해 판정 범위를 제한한다.
실제 대상 환경에서의 도달 가능성과 재현 여부는 별도 축이다. 최소화 과정에서 재현이
사라지면 마지막 성공 버전도 보존한다.

## 판정 기준

정적 단계의 상태는 보존하고 별도의 `Validation-status`를 부여한다.

| 상태 | 기준 |
|---|---|
| `DYNAMIC_CONFIRMED` | 명시된 환경에서 결함을 관측했고 지정된 후보의 근본 원인과 연결했으며 원본 증거와 재현 절차가 있다. |
| `OBSERVED_UNATTRIBUTED` | 이상 동작은 관측했지만 지정된 후보와 인과관계를 확인하지 못했다. |
| `NOT_REPRODUCED` | 기록된 조건과 시도 예산 안에서 재현하지 못했다. 반증을 의미하지 않는다. |
| `REJECTED` | 성립 불가능한 전제나 실제 방어 등 후보를 반증하는 구체적인 근거가 있다. |
| `NEEDS_CONTEXT` | 필수 소스·설정·환경·권한 정보가 없어 판정할 수 없다. |
| `INFRA_BLOCKED` | 이미지·부팅·도구·자원 문제로 유효한 실험을 완료하지 못했다. |

`DYNAMIC_CONFIRMED`는 입증한 환경에 한정한다. 한 번만 발생한 결과도 원본 증거와
인과관계가 충분하면 기록할 수 있으나 반복성의 한계를 명시한다. 크래시나 sanitizer 보고로
LPE, 임의 읽기·쓰기, 공식 대상 적격성 또는 플래그 획득을 입증했다고 주장하지 않는다.

## 종료와 인계

재현 및 인과 확인이 완료되거나, 후보가 반증되거나, 실행 예산·무진전 기준에 도달하거나,
필수 환경이 없으면 해당 후보의 실행을 종료한다. 무진전 반복을 무한히 연장하지 않는다.
남은 독립 후보는 계속 처리하고, 종료 사유와 후속 실험을 기록한다.

후보 디렉터리는 필요한 파일만 포함하되 다음을 재구성할 수 있어야 한다.

```text
environment.md       대상·설정·권한·VM 소유권·진단 조건
repro/               최종 재현기, 빌드·실행 절차, 필요한 입력
attempts/<run-id>/   명령, 입력, 출력, 콘솔·커널 원본 로그, 종료 사유
validation.md        인과 분석, 판정, 반복성, 한계와 다음 단계
SHA256SUMS           인계하는 소스·바이너리·설정·증거 파일의 해시
```

`validation.md`에는 Candidate-ID, Target-ID, 원본 정적 기록 경로, Validation-status,
실제 관측, 소스 연결, 도달 권한, 대상과 실험 환경의 차이, 성공/총 시도, 중요한 실패,
미확인 영향, 증거 경로를 포함한다. 실패한 시도도 재현 불가의 범위를 이해할 만큼 남긴다.

종료 전 `agent/<research-name>/FINDINGS.md`에 확인된 사실, 유용한 원시 효과,
중요한 부정적 결과, 미해결 사항, 증거 경로·해시를 기존 내용과 병합한다. 악용 가능성 평가나
패치 단계에는 이 자료를 인계하고, 해당 단계가 승인되었을 때만 진행한다.

## 설계 근거

OpenAI의 [루트 권한 탈취 경로 1,000개 줄이기](https://openai.com/ko-KR/index/a-thousand-fewer-paths-to-root/)
중 동적 검증 절차를 참고했다. 격리 환경의 최소 재현기, 실행 증거를 이용한 반복 개선,
정적 후보와 검증된 결과의 구분을 채택했다. 위 판정 상태와 파일 구조는 이 저장소의
인계·격리 규칙에 맞춘 운영 설계이며 원문의 공개되지 않은 내부 구현을 재현한 것은 아니다.
